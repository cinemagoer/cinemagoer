S3 datasets
===========

IMDb distributes part of its data as non-commercial downloadable `datasets`_.
Cinemagoer imports this data into a local database and accesses it through the
standard API.

SQLite access and importing use Python's standard-library ``sqlite3`` module,
so the base installation is sufficient::

   pip install cinemagoer

For PostgreSQL, MariaDB, MySQL, or an explicitly selected SQLAlchemy dialect,
install the optional integration and the DBAPI driver of your choice::

   pip install "cinemagoer[sqlalchemy]"
   # Also install psycopg, mysqlclient, or another suitable driver.

Cinemagoer supports all databases supported by SQLAlchemy. In this
documentation we use SQLite in examples because it is the simplest setup.

Then, follow these steps:

#. Download the files from https://datasets.imdbws.com/ and put all of them
   in the same directory.

   You can download all IMDb dataset files with the installed
   ``download-from-s3`` command::

      download-from-s3

   This creates a timestamped directory named like
   ``imdb-dataset-YYYY-MM-DD`` with the ``*.tsv.gz`` files.

#. Create or choose a database.

#. Import the data using the :file:`s32cinemagoer.py` script::

      s32cinemagoer.py /path/to/the/tsv.gz/files/ URI

   ``URI`` is the connection string used to access the database.

   For SQLite, use a URI like::

      s32cinemagoer.py ~/Downloads/imdb-datasets/ sqlite:///cinemagoer.db

   You can also use other SQLAlchemy-supported database URIs after installing
   the ``sqlalchemy`` extra and the appropriate database driver. Canonical
   ``sqlite:`` URIs always use the native adapter; an explicit dialect such as
   ``sqlite+pysqlite:`` selects SQLAlchemy instead.

   For faster local iteration while developing, you can create reduced
   dataset files with ``s3-reduce``::

      s3-reduce /path/to/the/tsv.gz/files/

   This writes smaller files under ``partials/`` in that directory.

PostgreSQL with Docker
----------------------

The following example starts PostgreSQL 17 in Docker and stores its data in a
named volume, so the imported database survives container restarts. Replace
the example password before using this setup beyond local development::

   docker volume create cinemagoer-postgres-data
   docker run --name cinemagoer-postgres --detach \
       --env POSTGRES_USER=cinemagoer \
       --env POSTGRES_PASSWORD=change-this-password \
       --env POSTGRES_DB=cinemagoer \
       --publish 127.0.0.1:55432:5432 \
       --volume cinemagoer-postgres-data:/var/lib/postgresql/data \
       postgres:17

Wait until PostgreSQL is ready to accept connections::

   until docker exec cinemagoer-postgres \
       pg_isready --username cinemagoer --dbname cinemagoer
   do
       sleep 1
   done

Install the optional SQLAlchemy integration and the PostgreSQL driver, then
import the datasets::

   pip install "cinemagoer[sqlalchemy]" "psycopg[binary]"

   export CINEMAGOER_DATABASE_URI='postgresql+psycopg://cinemagoer:change-this-password@127.0.0.1:55432/cinemagoer'
   s32cinemagoer.py /path/to/the/tsv.gz/files/ "$CINEMAGOER_DATABASE_URI"

Use the same URI in Cinemagoer:

.. code-block:: python

   import os

   from imdb import Cinemagoer

   ia = Cinemagoer('s3', uri=os.environ['CINEMAGOER_DATABASE_URI'])
   print(ia.get_movie('0133093'))

Stop the container with ``docker stop cinemagoer-postgres``. Start it again
with ``docker start cinemagoer-postgres``; the named volume retains the
database. The import command rebuilds Cinemagoer's tables, so do not run it
against a database containing data you need to preserve.

Once the import is finished - which should take about an hour or less
on a modern system - you will have a database with all the information
and you can use the normal Cinemagoer API:

.. code-block:: python

   from imdb import Cinemagoer

   ia = Cinemagoer('s3', uri='sqlite:///cinemagoer.db')

   results = ia.search_movie('the matrix')
   for result in results:
       print(result.movieID, result)

   matrix = results[0]
   ia.update(matrix)
   print(matrix.keys())


.. note::

   Running the script again will drop the current tables and import
   the data again.

   Databases imported before the cast-character fix have lost those names from
   ``title.principals.tsv.gz``. Back up the database, then run the import again
   with the original dataset files to restore them. They cannot be recovered
   from the existing database, and the import rebuilds the
   ``title_principals`` table.


Import safety and recovery
--------------------------

Before opening the destination database, ``s32cinemagoer.py`` validates that
the source directory contains all seven supported ``*.tsv.gz`` archives. It
reads every archive completely, verifies its header and row widths, exercises
the field transformations, and rejects empty or corrupt inputs. In-memory
SQLite destinations are rejected because closing them would discard the
finished import.

The import writes ``cinemagoer-import-manifest.json`` in the dataset directory.
The manifest records the Cinemagoer version, source filenames and sizes,
preflight and imported row counts, cleanup results, and completion status. Do
not switch applications to the rebuilt database until the status is
``completed`` and every table has matching non-zero row counts.

``--cleanup`` is irreversible. Source archives are removed only after every
table imports and the database transaction commits; each removed path is
logged. A failed import leaves all source archives in place and records a
``failed`` manifest.

SQLite and databases such as PostgreSQL that support transactional DDL can
roll back the complete multi-table import. Some databases, including MySQL and
MariaDB configurations, implicitly commit DDL statements. For those systems,
import into a new empty staging database, verify its completed manifest and
queries, then switch the application URI to the staged database. Keep the old
database and source archives until that switch has been validated.


Read-only query connections
---------------------------

Opening a file-backed SQLite URI with ``Cinemagoer`` never creates a database.
The file must already exist, and both the native ``sqlite:`` adapter and an
explicit SQLAlchemy SQLite adapter open it for read-only queries. Use
``s32cinemagoer.py`` when a database needs to be created or rebuilt.

The ``sqlite://`` and ``sqlite:///:memory:`` forms, and their explicit
SQLAlchemy equivalents, remain available for short-lived in-memory query
adapters. Their database exists only for the lifetime of that adapter and is
never written to the filesystem.
